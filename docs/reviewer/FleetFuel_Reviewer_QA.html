FleetFuel Q&A Reviewer

Performance of Linear Regression Model in Predicting Fuel Consumption for the Government Fleets · Guimaras State University GSO

Each item has the question, the short answer to say in the defense, and an In simple words explanation. Memorize the highlighted words.

A. About the System

1. What is your system?
A web-based fuel consumption prediction system for the GSU General Services Office (GSO) government fleet.
A website that estimates how many liters of fuel a vehicle will use on a trip.
2. What is the purpose of the system?
To predict the fuel (liters) needed for a trip so the GSO can release the right amount of fuel and monitor actual use.
So the fuel given is not too much or too little, and fuel use can be monitored.
3. Who are the users?
Administrator (one account) and GSO / motorpool staff.
The admin approves fuel requests and manages accounts; the staff make the predictions.
4. What are the main modules?
Login/Sign-up, Dashboard, Fuel Prediction, Prediction History, Trip Records, Vehicle Management, Model Performance, User Accounts, Account Settings, and the Notifications bell.
These are the pages you see in the system's sidebar.
5. How does a prediction work?
Staff select the vehicle and enter the distance; the system gets the engine power and fuel type from the vehicle record, and the model gives the predicted liters ± range. It becomes a fuel request for admin approval.
Just pick the vehicle and type the kilometers; the system does the computing.

B. Model / Algorithm

6. What model did you use?
Multiple Linear Regression.
Only one model is used: Linear Regression. No Random Forest, Decision Tree, SVR or any other model.
7. Why Linear Regression?
Because fuel use increases in a straight-line way with distance and engine power. It is simple, fast, accurate (R² 0.89) and easy to explain.
The longer the trip and the bigger the engine, the more fuel is used. The relationship is linear, so Linear Regression fits.
8. What is the equation of your model?
ŷ = β0 + β1(Distance) + β2(Engine Power) + β3(Fuel Type) + β4(Distance × Engine Power)
ŷ is the predicted liters; the β values are the numbers the model learned.
9. What is the fitted (final) equation?
ŷ = −1.7904 + 0.03263(D) + 0.03167(P) + 0(F) + 0.000573(D × P)
D = distance, P = engine power, F = fuel type. This is what the system uses to compute.
10. What is your dependent variable?
Fuel consumed per trip (liters).
This is what the model predicts.
11. What are your independent variables?
Distance (km), Engine Power (kW), Fuel Type (1 = Gasoline, 0 = Diesel), plus the Distance × Engine Power interaction term.
These are the inputs used to make the prediction.
12. What is the interaction term and why is it there?
Distance × Engine Power. A bigger engine burns more fuel per kilometre, so the effect of distance depends on engine power.
A bigger engine uses more fuel per kilometer, so we multiplied the two together.
13. Why is the Fuel Type coefficient 0?
The final model was trained on the fleet's range only, which is all diesel (30–400 km, 51–177 kW), so there was no gasoline difference to learn.
All GSU vehicles are diesel, so fuel type has no effect in the final model.
14. What library did you use to build the model?
scikit-learn (LinearRegression inside a Pipeline).
A Python library for machine learning.
15. How is the trained model saved and used?
Saved with Joblib as linear_regression_pipeline.joblib; Flask loads it to predict without retraining.
The model is saved in one file; the website just reads it for every prediction.
16. Where did you train the model?
In Google Colab (also possible with train_model.py); the model file is uploaded on the Model Performance page.
Training is done in Colab, then the model is uploaded to the system.
17. Does the system retrain by itself?
No. New data does not change the model until a new model is trained and uploaded.
The model does not change by itself; it must be retrained and uploaded.
18. What methodology did you follow?
CRISP-DM: Business Understanding → Data Understanding → Data Preparation → Modeling → Evaluation → Deployment.
Six steps for building a data mining / machine learning project.

C. Data

19. Where did your data come from?
GSO Monthly Report of Official Travel (93 trips of SFA 4714), the 9 fleet vehicle records, and two open online datasets: Fan & Song (2022) and the European Environment Agency (2024).
Our own data from the GSO plus two free datasets online.
20. How many records in total?
100,000 = 93 trips + 9 vehicles + 50,508 gasoline trips + 49,390 diesel vans.
This is all the data we gathered.
21. Why did you add online data?
The 93 local trips were too few and came from one vehicle only, so the model could not learn the effect of different engine sizes.
Our own data was not enough, so we added online data with the same variables.
22. How many records were used in training?
34,471 after cleaning (fleet range): 27,576 training (80%) and 6,895 testing (20%).
80% is used to teach the model; 20% is used to test it.
23. How did you clean the data?
Removed missing values and zero distance, removed outliers using the IQR rule, and kept only the fleet's range.
Wrong, incomplete and extreme records were removed.
24. How were trips and vehicles combined?
Merged using the plate number.
The plate number connects each trip to its vehicle.

D. Accuracy / Evaluation

25. How accurate is your model?
R² = 0.8877, MAE = 1.98 L, RMSE = 2.89 L.
The model explains about 89% of the changes in fuel use; it is off by only about 2 liters per trip.
26. What does R² mean?
The percentage of variation in fuel use explained by the model (0 to 1, higher is better). 0.8877 = 88.77%.
How well the model fits. The closer to 1, the better.
27. What do MAE and RMSE mean?
MAE = average error (1.98 L). RMSE = typical error that punishes big errors (2.89 L). Lower is better.
How many liters the prediction is off, on average.
28. How did you check that the model is not overfitting?
5-fold cross-validation: mean R² = 0.8879 ± 0.0015, almost the same as the test set.
We tested on five different parts of the data; the results were the same, so the model is stable.
29. What is the ± range shown in a prediction?
The prediction ± RMSE (2.89 L). If the actual fuel is outside it, the system flags the trip.
If the actual fuel used is outside the range, the system marks it.

E. Assumption Tests

30. What tests did you use for the regression assumptions?
Ramsey RESET (linearity), Durbin-Watson (independence), Jarque-Bera (normality), Breusch-Pagan (equal variance), VIF (multicollinearity).
Five tests, run with Statsmodels.
31. What is VIF and what is your result?
Variance Inflation Factor: checks if predictors overlap. Above 5 = problem. Ours: 1.01–1.03 → passed.
Checks whether the inputs repeat the same information. They do not, so it passed.
32. How did you reduce multicollinearity?
By mean-centering distance and engine power before multiplying them.
Their average is subtracted first before multiplying; this does not change the prediction.
33. Some tests did not pass. Is the model still valid?
Yes, for prediction. With over 30,000 records, even tiny deviations become "significant". We used HC3 robust standard errors, and accuracy is confirmed by the test set and cross-validation.
With a very large dataset, even tiny deviations show up in the tests. The predictions are still good.

F. Technology Used

34. What programming language did you use?
Python (back end) and HTML, CSS, JavaScript (front end).
Python runs the server; HTML/CSS/JS is what you see on the screen.
35. What web framework did you use?
Flask (Python).
It runs the website and connects it to the model and the database.
36. What database did you use?
Firebase Cloud Firestore (cloud NoSQL database).
Google's online database; it stores documents instead of tables.
37. Why Firestore?
It is free, cloud-based, real-time, and the data is safe even if the server PC turns off.
A change made on one computer shows up right away on the others.
38. What are the Firestore collections?
users, vehicles, trip_records, predictions, trip_dataset_changes, notification_dismissals.
Like tables, but Firestore calls them collections.
39. What front-end libraries did you use?
Bootstrap 5 (design/layout), Chart.js (charts), Font Awesome (icons), Poppins (font).
They make the website look good and work on any screen size.
40. What Python libraries did you use for data and ML?
Pandas (data tables), NumPy (math), scikit-learn (model), Joblib (save model), Statsmodels (statistical tests), Matplotlib and Seaborn (graphs).
These are the tools for processing the data and building the model.
41. What other back-end libraries did you use?
Werkzeug (password hashing), Flask-WTF (CSRF protection), firebase-admin (connect to Firestore), python-dotenv (secret settings), Waitress (production server).
For security, the database connection and running the server.
42. What tools did you use in development?
Visual Studio Code, Git & GitHub, Google Colab, Firebase Console, web browser.
Where we wrote, stored and tested the code.

G. Security

43. How are passwords protected?
Hashed with scrypt (Werkzeug); never stored as plain text.
The password is stored in a form no one can read, not even the admin.
44. What other security features does the system have?
CSRF protection, login required, role-based access (admin/staff), login lockout (5 wrong tries = 15 minutes), admin approval of new accounts, 8-hour sessions, and daily backups.
So people without permission cannot get in, and data is never lost.

H. Deployment

45. How do users access the system?
On the GSO network through the server PC (Waitress, port 5000), or online at gsu-fleetfuel.vercel.app.
In the office through the server PC, or online through the link.
46. What is Vercel?
A cloud hosting service that runs the online version; it auto-deploys from GitHub.
This is where the online link of the system is hosted.
47. How is the data backed up?
Automatic JSON backup every start and every 24 hours; the newest 30 are kept and can be restored.
A copy of the data is made every day in case something breaks.
