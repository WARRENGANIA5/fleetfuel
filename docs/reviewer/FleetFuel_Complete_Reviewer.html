Part II · Possible Questions and Answers

Short, simple answers. Say them with confidence, then stop. Red-bordered questions are the ones the panel is most likely to press on.

A. Title, Problem and Objectives

1.Explain your title.
It means we measured how accurately a Linear Regression model predicts the fuel a GSU vehicle uses per trip. "Performance" is measured by R², MAE and RMSE.
2.What problem does your study solve?
Fuel requests are approved by experience, and overuse is found only at liquidation, after the fuel is gone. Our system gives a computed fuel figure before the trip.
3.What is your general objective?
To develop and evaluate a Linear Regression model that predicts fuel consumption from the fleet's travel records, and integrate it into a web application.
4.What are your specific objectives?
Collect the data; clean and prepare it; build the model with an 80/20 split; evaluate it with R², MAE, RMSE and 5-fold cross-validation; build the web app; integrate the model; and implement it for users.
5.Did you meet all your objectives?
Yes. We collected 99,991 trip records, cleaned them to 34,111, trained the model with R² 0.9008, built and integrated the web app, and deployed it at gsu-fleetfuel.vercel.app.
6.What is the scope of your study?
The GSU fleet's diesel vehicles, trips of 30–400 km and engines of 51–177 kW, using a Linear Regression model inside a web application.
7.What are your limitations?
Our local records cover only one vehicle (SFA 4714) for six months, and its fuel follows a rule of 1 liter per 10 km. We only tested Linear Regression, and the system needs internet.
8.Who benefits from your study?
GSU, the General Services Office, the Transportation Office, the Chief Administration Office, the researchers, and future researchers.
9.What is the research gap?
Past studies used sensor or industrial data. None used manually written government travel records like the Monthly Report of Official Travel.
10.Explain your conceptual framework.
Input: travel records, vehicle records and online data. Process: data preparation, model development, evaluation and system development. Output: the trained model and the web application.
11.Why collect the date of travel if it is not a predictor?
We use it to arrange the 93 local trips in order for the Durbin-Watson test.

B. The System and Its Users

12.What is your system?
GSU FleetFuel, a website where staff choose a vehicle, type the distance, and get the predicted liters of fuel for the trip.
13.What are the modules?
Login and Sign-up, Dashboard, Prediction with Prediction History, Trip Records, Vehicle Management, Model Performance, User Accounts, Account Settings and Notifications.
14.Who are the users?
One Administrator, and the staff of the General Services Office and Transportation Office.
15.What can the Administrator do?
Approve or reject fuel requests, manage vehicles, trips and user accounts, and upload a new trained model.
16.What can the staff do?
Make fuel predictions, record the actual fuel after the trip, and view the dashboard and records.
17.How does a fuel request work?
Staff make a prediction, it becomes a pending request, the admin approves or rejects it, and after the trip the staff record the actual fuel used.
18.Why do users enter only the vehicle and the distance?
The engine power and fuel type are already in the vehicle record, so the system fills them in. This avoids typing mistakes.
19.What does the "±" range on the result mean?
It is the prediction plus or minus 2.66 liters, the model's typical error. If the actual fuel falls outside it, the system flags the trip.
20.What if the distance is outside 30–400 km?
The system still predicts but shows a warning, because the model was trained only within that range.
21.Only SFA 4714 has local trips. What about the other vehicles?
They can still be used because the model learned from many engine sizes, but the system warns that they are not yet validated with their own trips.
22.Can it be used on a phone?
Yes, through the phone's browser. The design adjusts to any screen size.

C. Technology Used

23.What programming language did you use?
Python for the back end and the model, and HTML, CSS and JavaScript for the pages.
24.Why Python?
Python is the standard language for machine learning. Our model and our website are in the same language, so the website can use the model directly.
25.Why Flask?
Flask is a lightweight Python web framework. It is simple, fits a small system like ours, and runs the model in the same program.
26.Why not Django or PHP?
Django has many features we do not need. PHP cannot run our Python model directly. Flask is the simplest fit.
27.What database did you use?
Firebase Firestore, a free cloud database by Google.
28.Why Firestore and not MySQL?
It is free, online and real-time. A change on one computer shows on all computers right away, and the data is safe even if the office PC is turned off.
29.What is NoSQL?
A database that stores data as documents instead of tables with rows and columns.
30.What is Bootstrap?
A design toolkit that makes the pages neat and fit on any screen size.
31.What is Chart.js?
A JavaScript library that draws the charts on the Dashboard and Model Performance pages.
32.What is Google Colab?
A free online Python notebook from Google. We used it to clean the data, train the model and test it.
33.What Python libraries did you use?
Pandas and NumPy for data, scikit-learn for the model, Joblib to save the model, Statsmodels for the statistical tests, and Matplotlib and Seaborn for the graphs.
34.Why scikit-learn and Statsmodels?
scikit-learn builds and tests the model. Statsmodels gives the statistical tests and p-values.
35.What is Joblib?
It saves the trained model into one file. The website loads that file to predict without retraining.
36.What is Waitress?
The server program that runs our website on the office computer, safe for many users.
37.What is Vercel?
A cloud hosting service where our online version runs at gsu-fleetfuel.vercel.app.
38.What tools did you use to develop it?
Visual Studio Code, Git and GitHub, Google Colab, the Firebase Console and a web browser.

D. Data

39.Where did your data come from?
From the GSO's Monthly Report of Official Travel (93 trips), the records of the 9 fleet vehicles, and two free online datasets: Fan & Song (2022) and the European Environment Agency.
40.What data does the travel report give?
The date of travel, the distance in kilometers and the fuel used in liters.
41.Why did you use online data?
Our 93 local trips come from one vehicle only. The online data has the same variables and lets the model learn the effect of different engine sizes.
42.Your local fuel follows 1 liter per 10 km. Is that real data?
It is the GSO's allocation, not a measured value, and we state this in our limitations. That is why we added measured online data, and the system now records the actual fuel after every trip.
43.Are the 7,496 online trip records real GSU trips?
No. They are real diesel van records from the EEA, matched to a fleet vehicle with a similar engine. We label them clearly as online data.
44.How many records do you have?
99,991 trip records plus 9 vehicle records, a total of 100,000. After cleaning, 34,111 remained.
45.Are you allowed to use the online data?
Yes. Both are under the CC BY 4.0 license, which allows use as long as we cite them, and we did.
46.How did you combine trips and vehicles?
We merged them using the plate number.
47.How did you clean the data?
We removed missing values, zero distances and outliers, and kept only the fleet's range: diesel, 30–400 km, 51–177 kW.
48.What is the IQR method?
A way to find outliers. A value is removed if it is far below the first quartile or far above the third quartile, by 1.5 times the IQR.
49.Why apply IQR by engine power group?
So big engines are compared only with big engines. Otherwise they would look like outliers just because they use more fuel.
50.How many records were removed?
65,520 records: 3,857 outliers and 61,663 outside the fleet's range. All 93 local trips were kept.
51.Why remove all the gasoline records?
All nine GSU vehicles are diesel, so gasoline data would describe vehicles the GSO does not have.
52.Why 30–400 km and 51–177 kW?
51 kW is the smallest engine in the fleet and 177 kW is the biggest. Local trips run from 32 to 372 km.
53.Why not use speed, road condition or cargo?
The travel report does not record them. We recommend adding them in future studies.

E. The Model

54.What is Linear Regression?
A model that predicts a number using a straight-line formula of the inputs.
55.Why Linear Regression and not Random Forest or neural networks?
Fuel use goes up almost in a straight line with distance, so it fits well with R² 0.89. It is also simple and easy to explain: each number shows how many liters a kilometer adds.
56.How does it learn the coefficients?
By Weighted Least Squares: it finds the line with the smallest total squared error, but long trips (which have bigger errors in liters) count less, so every trip is treated fairly.
57.What is your equation?
ŷ = −0.6054 + 0.02695(Distance) + 0.01966(Engine Power) + 0.000625(Distance × Engine Power)
58.What are your dependent and independent variables?
Dependent: fuel used per trip in liters. Independent: distance, engine power and their interaction.
59.What do the coefficients mean?
Each kilometer adds about 0.087 liters, about 8.7 liters per 100 km. Bigger engines add more fuel per kilometer.
60.What is the interaction term?
Distance multiplied by engine power. It shows that a bigger engine uses more fuel for every kilometer.
61.Why is the intercept negative?
The intercept is the value at 0 km and 0 kW, which is outside our data. Within 30–400 km all predictions are positive.
62.What is mean-centering?
We subtract the average from distance and engine power before multiplying them. It removes overlap between the variables without changing the predictions.
63.Why is the Fuel Type coefficient zero?
All our final records are diesel, so fuel type never changes and has no effect.
64.Which predictor is the strongest?
Distance, with a correlation of 0.88 to fuel used.
65.What is a Pipeline?
It packs the preprocessing steps and the model into one file, so every prediction follows the same steps as training.
66.Does the system retrain by itself?
No. A new model is trained in Google Colab, checked, then uploaded on the Model Performance page.
67.Why not retrain automatically?
So no new model is used before someone checks its accuracy.

F. Accuracy and Evaluation

68.How accurate is your model?
R² is 0.9008, MAE is 1.87 liters and RMSE is 2.66 liters.
69.What does R² 0.9008 mean?
The model explains about 90% of the changes in fuel use.
70.What do MAE and RMSE mean?
MAE: the prediction is off by about 2 liters on average. RMSE: about 2.9 liters, which gives more weight to big errors.
71.Why is RMSE higher than MAE?
Some long trips have bigger errors than the usual trip.
72.Why an 80/20 split?
80% to train the model and 20% to test it on data it has never seen. It is the common standard.
73.What is cross-validation?
We split the data into 5 parts and tested 5 times, each part once. The average R² was 0.9002.
74.Is your model overfitting?
No. The test R² (0.9008) and the cross-validation R² (0.9002) are almost the same.
75.What is random_state 42?
A fixed seed so we get the same split and the same results every time.
76.Your accuracy is tested mostly on online data. Does it work for GSU?
For a typical SFA 4714 trip of 176 km it predicts 16.46 liters, close to the recorded 17.6 liters. More local trips will make it more accurate.

G. Assumption Tests

77.What are the assumptions of linear regression?
Linearity, independent errors, normal errors, equal variance, and no multicollinearity.
78.What tests did you use?
Ramsey RESET, Durbin-Watson, Jarque-Bera, Breusch-Pagan and VIF.
79.What were the results?
All five passed: linearity, independence (Durbin-Watson 1.694), normality, equal variance and no multicollinearity (VIF 1.03).
80.Some p-values are still below 0.05. Why do you say the tests passed?
With 27,288 training records, a p-value flags even differences too small to matter. So for linearity, normality and equal variance we judged the size of the difference: Cohen's f² 0.0003 (below 0.02), skewness 0.37 and kurtosis −0.11 (within ±2 and ±7), and a variance ratio of 1.26 (at most 3). These are standard rules for large samples (Kim, 2013; Cohen, 1988; Dean & Voss, 1999).
81.What is VIF?
It checks whether the predictors repeat the same information. Above 5 is a problem; ours is only 1.03.
82.What is heteroskedasticity, and how did you fix it?
The errors in liters are bigger for long trips. We fixed it with Weighted Least Squares: each trip is weighted by 1 ÷ its expected error variance, so the weighted errors have the same spread for short and long trips. We also removed the 360 records (about 1%) whose standardized error was beyond ±3.
83.What does Durbin-Watson 1.694 mean?
It is between 1.5 and 2.5, so the errors of consecutive local trips (arranged by date) are independent. We removed their average error of +1.14 L first, because a constant difference for one vehicle is not a relation between trips.
84.What is a residual?
The actual value minus the predicted value.
85.What does p < 0.05 mean?
The result is statistically significant. All our coefficients have p below 0.001.

H. How the System Uses the Model

86.How does a prediction work inside the system?
Flask loads the saved model, gets the vehicle's engine power from the database, applies the same steps as training, and shows the liters.
87.What is your system architecture?
Three layers: the browser (the pages), Flask with the model (the processing), and Firestore (the data).
88.How do pages update without reloading?
JavaScript asks the server for new data every few seconds.

I. Database

89.What collections are in your database?
users, vehicles, trip_records, predictions, trip_dataset_changes and notification_dismissals.
90.What links trips and vehicles?
The plate number.
91.How is the data real-time?
Firestore sends every change to the server immediately, so all users see the same data.
92.Is Firestore free?
Yes, the free plan allows 50,000 reads a day, and our system stays within it.
93.What if the internet is down?
The system needs internet, as stated in our limitations. The data is still safe in the cloud.
94.How is the data backed up?
The system backs up the whole database every time it starts and every 24 hours.

J. Security

95.How are passwords protected?
They are hashed with scrypt, so no one can read them, not even the admin.
96.What other security features does it have?
Login is required for every page, staff cannot open admin pages, logins lock after 5 wrong tries, new accounts need admin approval, and forms are protected against CSRF.
97.What is CSRF?
An attack where another website submits a form using your login. A secret token on every form blocks it.
98.Can staff inflate the distance to get more fuel?
Every request is recorded and reviewed by the admin, and the actual fuel is compared after the trip. Unusual use is flagged.

K. Deployment

99.How do users open the system?
In the office through the server computer, or online at gsu-fleetfuel.vercel.app. Both use the same database.
100.How is the online version updated?
When we push code to GitHub, Vercel updates the site automatically.
101.What do users need?
Only a web browser and an internet connection.

L. Methodology

102.What methodology did you use?
CRISP-DM: Business Understanding, Data Understanding, Data Preparation, Modelling, Evaluation and Deployment.
103.Why CRISP-DM?
It is the standard process for data and machine learning projects, and it lets us go back to earlier steps when needed.
104.Give an example of going back to an earlier phase.
After seeing all GSU vehicles are diesel, we went back to data preparation, kept only the fleet's range, and retrained the model.

M. Conclusions and Recommendations

105.What is your main conclusion?
Linear Regression predicts the fleet's fuel use well, explaining about 89% with about 2 liters of error, and gives the GSO a computed basis for approving fuel.
106.What are your recommendations?
Record the actual fuel of every trip, collect records from all nine vehicles, retrain the model regularly, and let future researchers add more variables and compare other models.

N. Hard Panel Questions

107.What is your contribution?
We showed that the GSO's paper travel records, combined with open data, can power a working fuel prediction system, and we give a baseline for future studies.
108.Does the system approve the fuel?
No. The prediction is only a reference; the administrator makes the decision.
109.Your data is mostly foreign. Why should it apply to Guimaras?
We kept only diesel vehicles with the same engine sizes as our fleet. More distance and bigger engines mean more fuel anywhere. Local trips will make it more accurate over time.
110.Why is the prediction lower than SFA 4714's records?
The records follow the 1 L per 10 km allocation. Measured data shows similar vans use about 8.7 L per 100 km, so the allocation may be a little generous.
111.What if a new vehicle is added?
If it is diesel with 51–177 kW, the admin just adds it and it works right away. Otherwise the model should be retrained.
112.How did you test the system?
We tested every feature in actual use: predictions, approvals, actual fuel recording and sign-ups, both in the office and online. A user survey can be a future recommendation.
113.Who will maintain it after you?
The GSO admin manages everything through the website. Retraining is documented step by step, and backups run automatically.
114.What would you improve?
Collect measured fuel from all nine vehicles, add variables like speed and load, and compare with other models.

Part III · Demo Script, Formulas and Glossary

Suggested live demo (5 minutes)

  1. Login as staff → show the Dashboard (live cards and charts).
  2. Prediction → select SFA 4714 → enter 176 km → result ≈ 16.46 L ± 2.66 L. Point out that engine power and fuel type came from the vehicle record.
  3. Try a vehicle without local trips (e.g., SFA 1741) → show the "not validated" warning. Try 450 km → show the out-of-range warning.
  4. Switch to the admin → bell shows the new request → Prediction History → approve and set the liters to release.
  5. Back as staff → bell shows "approved" → record the actual fuel → show the "outside the predicted range" flag if it differs by more than 2.66 L.
  6. Trip Records → the Pending trip added by the request; the 93 SFA 4714 trips.
  7. Model Performance → R², MAE, RMSE, CV, VIF, assumption tests, charts; mention the Colab upload.
  8. User Accounts → approve a sign-up; mention password hashing and lockout.

Formulas

R² (coefficient of determination)

R² = 1 − Σ(yᵢ − ŷᵢ)² / Σ(yᵢ − ȳ)²

MAE

MAE = (1/n) Σ |yᵢ − ŷᵢ|

RMSE

RMSE = √[ (1/n) Σ (yᵢ − ŷᵢ)² ]

VIF

VIFj = 1 / (1 − Rj²) · above 5 = high collinearity

IQR outlier rule

IQR = Q3 − Q1 · keep Q1 − 1.5·IQR ≤ x ≤ Q3 + 1.5·IQR (on L/100 km, per engine-power group)

Centering

Dc = D − 151.209 · Pc = P − 95.3679 · interaction = Dc × Pc

Residual

eᵢ = yᵢ − ŷᵢ (actual − predicted)

Weighted Least Squares

minimize Σ wᵢ(yᵢ − ŷᵢ)² · wᵢ = 1 / exp(γ₀ + γ₁ log ŷᵢ) (γ₀ = −4.46, γ₁ = 1.87)

Standardized residual

zᵢ = (yᵢ − ŷᵢ)√wᵢ / s · records with |zᵢ| > 3 removed

Fuel per 100 km

L/100 km = fuel ÷ distance × 100

Glossary

TermSimple definition
Dependent variableWhat the model predicts: fuel consumed (L).
Independent variable / predictorInputs used to predict: distance, engine power (and the interaction).
Coefficient (β)How much the prediction changes per 1-unit increase in a predictor.
Intercept (β₀)Prediction when all predictors are 0 (or at their means, in the centered form).
OLSOrdinary Least Squares — finds coefficients that minimize squared errors.
WLSWeighted Least Squares — like OLS, but each record has a weight; used here so long trips with bigger errors count less.
Interaction termProduct of two predictors so one's effect depends on the other.
MulticollinearityPredictors carrying the same information; measured by VIF.
HeteroskedasticityError spread not constant (grows on long trips). Fixed with Weighted Least Squares.
AutocorrelationErrors of consecutive records related to each other (Durbin-Watson).
OverfittingModel memorizes training data and fails on new data.
Cross-validationRepeated train/test on different parts of the data to check stability.
OutlierAn extreme value far from the rest; removed with the IQR rule.
EncodingTurning categories (Gasoline/Diesel) into numbers (1/0).
PipelinePreprocessing + model chained into one saved object.
JoblibLibrary that saves and loads the trained model file.
Flask / WSGI / WaitressPython web framework / standard app-server interface / production server.
Firestore / NoSQLGoogle cloud database storing documents in collections, without tables.
Snapshot listenerFirestore feature that pushes every change to the server instantly.
CSRFAttack submitting forms as the user; blocked by a secret token.
Hashing (scrypt)One-way scrambling of passwords so they cannot be read back.
Serverless (Vercel)Code runs on demand in the cloud without managing a server.
